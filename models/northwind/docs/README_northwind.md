# Northwind Sales Insights — Project Reflection

## What business problem does this dbt model solve?

Northwind Trading distributes food and beverage products worldwide, and their analytics team faced three real problems with the raw data: inconsistent column names and types spread across separate order, product, and category tables, analysts repeatedly writing the same long SQL joins to answer basic sales questions, and no single agreed definition of "revenue," so two people could report two different numbers for the same period. This project builds a layered dbt pipeline, staging, prep, and mart, against the real `northwind` schema, so the cleaning happens once, the definition of revenue is calculated once, and every downstream user works from one trusted table instead of rebuilding the same logic from scratch.

## Which models did I build, and what does each do?

- **Staging models** (`staging_nw_orders`, `staging_nw_order_details`, `staging_nw_products`, `staging_nw_categories`): each pulls from one raw table in the `northwind` schema, casts dates to `DATE` and prices and quantities to numeric types, and keeps only the columns needed downstream. The `categories` table here is a genuine standalone table with its own `category_id` and `category_name`, so this layer stayed close to the classic Northwind structure.
- **Prep model** (`prep_nw_sales`): joins the four staging models on `order_id`, `product_id`, and `category_id`, calculates `revenue` as `unit_price * quantity * (1 - discount)` for every order line, and extracts `order_year` and `order_month` from the order date. It uses a `LEFT JOIN` to `categories` specifically because a product could in principle be missing a category match, and a plain `JOIN` would silently drop that revenue row rather than surfacing it as unknown.
- **Mart model** (`mart_nw_sales_performance`): aggregates `prep_nw_sales` by year, month, and category into `total_revenue`, `total_orders`, and `avg_revenue_per_order`, the table a BI tool or dashboard would query directly.

I also wrote a `schema.yml` with `not_null` tests on every mart column, run with `dbt test`. All six tests currently pass, confirming there are no broken joins or missing values reaching the final table.

## What insights can this mart provide to Northwind?

The mart covers July 1996 through May 1998 across eight categories, Beverages, Condiments, Confections, Dairy Products, Grains and Cereals, Meat and Poultry, Produce, and Seafood. A few patterns stand out directly from the data: **Beverages** and **Dairy Products** together account for close to forty percent of total revenue, and **Beverages** shows the widest month to month swings in average revenue per order, driven by a handful of high unit price items. Comparing `total_orders` against `avg_revenue_per_order` across categories also separates "high volume, lower ticket" categories like Seafood from "lower volume, higher ticket" ones like Meat and Poultry, exactly the kind of distinction that should shape whether a category's growth strategy focuses on order volume or basket size. Revenue also climbs sharply into early 1998 compared with the same months a year earlier, a signal worth investigating further.

## What was my biggest learning moment in this project?

The real schema did not match the assignment's sample solution, and that mismatch was the most useful part of the exercise. The `northwind` upload turned out to already use snake_case columns, `order_id` instead of `orderid`, which broke my first run with a `column "categoryid" does not exist` error until I actually queried `SELECT * LIMIT 1` on each raw table and rewrote the staging models to match what was really there instead of trusting the sample SQL. I also hit a naming collision: because this pipeline lives in the same dbt project as an earlier pipeline built for a different schema, reusing familiar model names like `staging_orders` caused a duplicate model name compile error, solved by prefixing every model in this pipeline with `nw_`. Both problems reinforced the same lesson, dbt's layered structure is only as reliable as the assumptions built into the staging layer, so verifying the real schema before writing a single line of SQL is not optional, it is the actual first step of the job.
